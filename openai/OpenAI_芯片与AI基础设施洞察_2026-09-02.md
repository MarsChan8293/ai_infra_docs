# OpenAI 芯片与 AI 基础设施洞察（截至 2026-09-02）

> 研究日期：2026-09-02 | 访问日期：2026-09-02 | 研究对象：OpenAI 芯片、基础设施及相关合作 | 证据优先级：OpenAI、合作方官方公告、SEC/交易所文件

## 一句话结论

截至 2026-09-02，OpenAI 已从“主要采购并共同优化外部加速器”走到“公开确认拥有第一代自研推理芯片 Jalapeño 的工作样片和实测结果”，但仍处在工程样片/初步部署前阶段；OpenAI 的真正战略资产不是替代所有 GPU，而是把模型、kernel、serving、内存、网络、调度和数据中心做成可切换的全栈组合，用自研 ASIC 在高规模推理上取得成本、延迟和能效杠杆，同时继续依赖 NVIDIA、AMD、AWS Trainium、Cerebras、Broadcom、Microsoft、Oracle、CoreWeave 和 SoftBank 等外部体系。

### 结论性的边界声明

“OpenAI 自研芯片”现在已经不能再写成“公开资料未确认”。更准确的表述是：**Jalapeño 已被 OpenAI 官方确认是 OpenAI 的第一款自定义推理芯片，并有工程样片与公开测量；但除 tape-out/送样/实验室运行/初步部署路线图之外，量产、出货、客户部署和云可用仍未被官方明确确认。**

## 3. 芯片、板卡、系统、数据中心、云和模型的边界

```text
模型与产品：GPT / ChatGPT / Codex / Frontier / API
          ↓ 产生真实 kernel、serving、延迟、吞吐、KV 与可靠性约束
软件：kernel、编译/编程、serving、调度、故障恢复、MRC
          ↓
芯片：Jalapeño（OpenAI 设计；Broadcom 实现协作）
板卡/机架/系统：Celestica 集成；Broadcom 网络/连接
          ↓
数据中心与电力：Stargate、Microsoft、Oracle、AWS、CoreWeave、SoftBank
          ↓
云服务：Azure、OCI、AWS Bedrock 等向客户提供模型或 agent 能力
```

这条链条中，只有中间的 Jalapeño 可称为 OpenAI 自研/主导设计芯片。NVIDIA GB200/Vera Rubin、AWS Trainium、Cerebras 系统、AMD Instinct、Broadcom Tomahawk 都属于合作方或外部硬件。ChatGPT、Codex、GPT-5.5、Frontier、Amazon Bedrock 则属于模型/产品/云分发层。

## 4. 架构洞察

### 4.1 Jalapeño 的公开架构信号

官方没有公布 ISA、矩阵阵列尺寸、片上存储层级、HBM 代际、片间协议或芯片拓扑。因此下面只写到公开证据能支撑的层级。

**官方事实：** Jalapeño 是从零面向现代 LLM 推理设计，不是把早期 AI 工作负载的通用加速器改造过来。设计输入包括 OpenAI 的模型路线图、kernel、serving 系统和产品需求，目标是在单一架构中兼顾高吞吐与低延迟。

**官方事实：** OpenAI 指出架构会减少数据移动，并平衡计算、内存、网络资源，使实际利用率更接近理论峰值；Richard Ho 进一步点名 kernel、memory movement、networking 和 serving patterns。

**分析判断：** 这不是“只堆 TOPS”的路线。它更像把推理中的流水线空转、权重/激活/KV 搬运、跨核/跨芯片同步和 serving 调度共同纳入 ASIC 的优化目标。由于 decode 常受内存带宽和访问延迟限制，若设计能把热数据、算子执行和网络通信放在更短的数据路径上，性能/瓦和 token latency 可能同时改善；但公开资料不足以判断它采用了哪一种具体内存或互联实现。

### 4.2 训练与推理的分工

Jalapeño 的公开定位是 inference-first。OpenAI 的整体组合仍覆盖：

- NVIDIA 系统承担已公开的 Stargate 训练/推理与 Vera Rubin 路线。
- AWS 通过 NVIDIA GPU 和 Trainium 承担云内工作负载。
- Cerebras 提供超低延迟推理容量。
- Jalapeño 以高规模、互动式、成本敏感的 LLM 推理为第一落点。

**分析判断：** 这是一种“训练保持外部多供应商、推理逐步加入自研 ASIC”的风险分层。训练更看重生态成熟度、可编程性、集群规模和长时间故障恢复；推理更容易围绕有限的 serving 模式、量化策略、KV 管理和产品延迟目标做定制。不能据此断言 Jalapeño 已被用于训练。

### 5.2 KV Cache 的关系

**官方事实：** OpenAI 的 Jalapeño 初步结果文章将现代 LLM 推理拆成不同瓶颈，并在架构讨论中强调内存移动、延迟和完整请求测量；官方没有公开“KV Cache 容量”“每 token KV 字节数”“KV 是否片上/片外”“跨芯片 KV 放置策略”。

**分析判断：** 对自回归 decode，权重读取和 KV 读取会反复发生，KV 的容量、带宽、局部性与调度决定并发上限。Jalapeño 若能减少权重、激活与 KV 的往返，或在服务层把 KV 放置与网络拓扑共同规划，就可能解释其“低延迟 + 高吞吐”的目标。但这仍是架构推理，不是公开规格。

## 6. 软件生态与可编程性

**官方事实：** OpenAI 说模型加速了 Jalapeño 的设计和 bring-up，最新模型正在加速芯片优化和编程；文章标题和正文还称“designed the chip so AI could program it”。OpenAI 同时把 kernel、serving、调度和部署系统列入全栈设计范围。

**分析判断：** “AI 可编程”更可能表示由模型辅助生成/优化 kernel、映射和调度，而不是芯片自动获得无限泛化能力。真正的生态风险仍在于：算子覆盖、编译器稳定性、调试工具、数值一致性、量化/稀疏支持、模型变更时的重新编译速度，以及外部模型接入成本。

OpenAI 的多供应商策略降低了单一硬件失败的风险，但也要求 serving 抽象、算子库、性能模型和调度器具备硬件可移植性。MRC 作为 OCP 开放协议，体现的是网络层标准化；它不等于 Jalapeño 软件栈已向公众开放。

## 7. 场景与性能证据

### 7.1 适合的场景

- ChatGPT 的互动式回答，尤其是对首 token 和端到端响应敏感的请求。
- Codex 和 agent，多步调用会把每一步的延迟累加。
- API 高并发推理，重点是 tokens/user、tokens/watt、单位请求成本和稳定性。
- 对模型架构相对稳定、能长期积累 kernel/serving 优化的内部工作负载。

### 7.2 官方公布的性能数字

2026-08-25，OpenAI 在公开的 SemiAnalysis InferenceX 基准上报告：

- 使用 GPT-OSS 120B、DeepSeek R1、Kimi K2.5 1T 三类模型。
- 峰值吞吐下，每瓦 AI 工作量为对比系统的 **1.5–1.9 倍**。
- 端到端延迟为对比系统的 **1.7–3.6 倍更低**。
- 高互动工作负载下，性能为对比系统的 **2.1–4.1 倍**。

这些数字是 OpenAI 对自身测试的官方披露，属于“合作方/产品方主张的实测结果”，不是独立复现实验。报告没有在公开页面给出足以复算的完整硬件配置、功率边界、批大小、序列长度、量化配置、并发点、对比系统型号和价格，因此不能把它们直接转成通用芯片性能排名或 TCO 结论。

## 8. Search、Top-k、Gather、KV 与通信的关系

这里的 Search/Top-k/Gather 不是 OpenAI 已公开的 Jalapeño 指令集规格，而是把其公开的 LLM serving、内存搬运和网络目标映射到常见工作负载后的分析框架。

### 8.1 Search / Top-k

MoE 路由、候选选择、检索增强和 beam-like 选择都可能出现 Search/Top-k。Top-k 的瓶颈通常包括比较、归约、索引生成和不规则内存访问。若硬件只优化矩阵乘，Top-k 仍会让计算单元等待；OpenAI 反复强调 kernel、serving 和数据搬运，说明这类非 GEMM 阶段可能属于系统优化范围，但官方没有确认 Jalapeño 有专用 Top-k 单元。

### 8.2 Gather

Gather 把索引转成权重、激活、KV 或专家数据访问，容易受内存局部性和跨芯片通信影响。OpenAI 的“减少 data movement”目标与 Gather 的问题高度相关，特别是 MoE expert dispatch、KV 读取和检索结果拼接。这里是架构意义上的对应关系，不是公开的 Jalapeño 功能清单。

### 8.3 KV

decode 阶段以 token 为粒度推进，KV Cache 读写与并发规模强相关。高吞吐与低 TBT/端到端延迟常有冲突：批量变大可提高利用率，但会增加排队和内存压力。OpenAI 称 Jalapeño 试图在单一架构中同时改善吞吐和延迟，合理的解释是其芯片、内存、网络和 serving 共同调度，而不是只提高矩阵算力。

### 8.4 通信

训练中的 all-reduce、all-to-all 和 checkpoint 恢复会把网络故障放大。OpenAI 的 MRC 通过多路径、adaptive packet spraying、静态源路由与故障绕行，目标是让同步训练少因链路抖动重启。Broadcom 的 Ethernet/Tomahawk 则提供交换和互联硅。它们说明 OpenAI 的基础设施洞察已经把“数据搬运”和“通信可靠性”放到与加速器同一层级；但 MRC 是训练网络协议，不能被说成 Jalapeño 的片内互联协议。

## 9. 冲突、边界与未确认项

### 9.1 “10GW”不能重复相加

OpenAI 同期公布 Broadcom 10GW、NVIDIA 至少 10GW、Stargate 10GW、AWS 380亿美元与 2GW Trainium、Cerebras 750MW 等数字。它们可能在时间、站点、供应商和工作负载上重叠，不能简单相加得到 OpenAI 已拥有的芯片数量或独立算力。

### 9.2 “自研”与“自主制造”不同

Jalapeño 的公开表述是 OpenAI 设计，Broadcom 做芯片实现、网络和连接，Celestica 做板卡/机架/系统工业化。没有公开证据表明 OpenAI 自有晶圆厂、封装厂或完整制造链。TSMC 官方页面/公告检索截至 2026-09-02 未找到 OpenAI 项目的直接确认，因此报告不把 TSMC 写成 Jalapeño 的已确认代工方。

### 9.3 “first custom inference chip”不等于“所有 OpenAI 芯片”

Jalapeño 是第一款公开确认的自定义推理芯片。它不证明 OpenAI 已有公开的训练芯片、CPU、NIC、HBM 或 DPU 型号，也不证明所有 OpenAI 工作负载已迁移。

### 9.4 “云可用”必须单独核验

OpenAI 模型在 Azure、AWS Bedrock 或其他平台可用，只说明模型/产品分发或云承载路径。除非出现明确的实例类型、租户入口、部署说明或客户公告，否则不能写成 Jalapeño 已云可用。

### 9.5 性能结果的证据等级

Jalapeño 的性能是 OpenAI 发布的初步结果，页面称详细技术报告将在后续提供。当前不能把“industry-leading”当作独立基准事实，也不能在缺少完整测试配置时声称其优于所有 GPU/ASIC。

## 10. 横向位置与未来判断

OpenAI 的选择不是单路线替代，而是组合优化：NVIDIA 提供成熟训练与通用生态，AMD 增加供应与路线选择，AWS Trainium 提供云内专用 ASIC，Cerebras 提供极低延迟特化系统，Broadcom 提供定制硅与 Ethernet 网络，Microsoft/Oracle/CoreWeave/AWS 提供数据中心和云容量，OpenAI 自己把最贴近产品的推理约束固化进 Jalapeño。

**最可能情景（分析判断）：** Jalapeño 先在 OpenAI 内部高量推理与 agent 场景扩容，与 NVIDIA/Trainium/Cerebras 按工作负载分工；OpenAI 继续公开性能和软件接口，但不把芯片作为独立商品销售。

**最危险情景（分析判断）：** tape-out 速度快于软件生态成熟速度，模型路线变化、算子覆盖、内存容量或系统可靠性成为瓶颈，导致纸面性能无法转成每请求成本和可用性；同时 10GW 项目的电力、封装、网络和交付节奏出现错配。

**最乐观情景（分析判断）：** OpenAI 把真实 serving 数据持续反馈给芯片、内存、网络和调度，Jalapeño 多代产品在推理成本/延迟上形成稳定优势，外部供应商保留训练与峰值能力，OpenAI 通过组合调度获得更高的供给弹性和议价权。
