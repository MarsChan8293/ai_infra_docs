00 / 先把问题讲人话

GPU 像矩阵工厂，Indexer 更像“搜索引擎 + 地址簿”。

Tensor Core 擅长大块、整齐的矩阵计算。本文关注的检索式或动态稀疏长上下文推理，还需要在大量历史位置中找候选、保留 Top-k、把逻辑位置翻译成 KV 页地址，再读取分散的数据。后半段经常受数据移动和通信影响，不能只靠增加矩阵算力解决。

现有强项

规则计算已经很强

GEMM、FFN 和密集 Attention 可以把规则数据喂给矩阵单元，追求高吞吐。

新增压力

动态数据不够整齐

Indexer、Top-k、page map 和 KV Gather 需要比较、筛选、生成离散地址，并连接下一步计算。

真正目标

优化一个 token 的旅程

关注 TPOT、HBM bytes/token、跨卡 bytes/token 和 Tokens/J，而不是只让单个 kernel 的峰值更好看。

技术类比：把长上下文看成一个大型数据集合。Query 是检索条件，Indexer 负责给候选位置打分，Top-k 保留最相关的位置，Gather 按这些位置取回 KV，Attention 再对取回的数据做深入计算。

类比边界：真实芯片没有运行通用数据库；这个类比只解释为什么“检索、地址和搬运”会形成一条与矩阵计算不同的数据路径。

01 / 新路径

把推理芯片拆成“密集计算平面 + 检索搬运平面”。

Retrieval Plane 不是缩小版 Tensor Core，也不绑定某个模型公式。它把 Search、Reduce、Top-k、Gather、Route 和 Page Map 组合成可编程的数据流；Tensor Plane 继续做最擅长的规则计算。

R-Plane / proposed inference architecture

让有用的数据更早留下，让无用的中间结果更早消失。

Tensor Compute Plane

吞吐导向，处理规则、密集的矩阵与向量计算。

GEMMGEMVFFNATTENTIONMOE

Retrieval / Data-Movement Plane

数据流导向，处理动态索引、候选筛选、地址翻译和离散搬运。

矩阵单元 + 向量单元 + 软件可控片上中间存储这是一条可迁移的共同设计原则：矩阵结果留在 UB、SMEM/TMEM、SBUF、VMEM 或 L1 等片上工作区，直接交给向量单元处理，尽量不绕回 HBM；Descriptor Queue 负责把搬运和依赖串起来。

最关键的并行变化：除了按 Attention/Indexer head 切分，还可以沿历史 candidate 或 block 切分。每个分区先做 Local Top-k，再合并约 P×k 规模的候选。它减少的是通信对象和中间结果；在没有额外索引时，精确扫描本身仍可能是 O(L)。

Partition 0 · Local Top-k+Partition 1 · Local Top-k…Partition P · Local Top-k→Global Merge→Page-aware Gather

先保持结果语义，减少搬运和通信

流式产生 score，在每个分区做 Local Top-k，再做 Global Merge，并直接生成 Gather descriptor。第一阶段不承诺降低全量扫描复杂度。

Full scan O(L) · merge input ≤ P × k candidate records

这里的 P×k 描述合并输入的候选数量上界，不直接等于通信字节或 collective 复杂度；实际成本还取决于候选记录大小、拓扑和 collective 实现。

再用层级索引减少需要扫描的候选

加入 block summary、层级索引、候选 refinement 或跨层复用。它可能减少扫描量，但会引入 recall、模型质量和算法协同约束。

coarse blocks → fine candidates → exact rerank → Top-k
02 / 第一验证

先用软件证明端到端价值，再决定哪些能力值得划进硅。

第一版实验应保持 Exact 结果，对比现有 full-score 路径、流式融合路径和 candidate-sharding 路径。只有收益穿透到 TPOT、数据移动、通信和能耗，专用 Retrieval Plane 才有面积价值。

P0

先打通数据流

强 Vector、Shared SRAM/UB、异步 DMA、Streaming Reduction + Top-k，以及持久化 descriptor queue。

P1

形成硬件差异化

Retrieval Core、candidate 分片、KV Page Translator、Local Top-k 和 Merge Top-k collective。

P2

再走向近存与近似

HBM-side retrieval、层级索引 SRAM、跨层索引缓存和 Approximate Search。

GO / 进入硬件可行性评估

如果 Exact 软件原型减少 HBM 或跨卡通信，而且最终 TPOT、吞吐或 Tokens/J 有可重复的改善，再继续评估面积、功耗、时序和工作负载覆盖面。

NO-GO / 暂不划硅

只有 Indexer 单 kernel 变快，端到端指标几乎不动，说明系统瓶颈还没有被真正移动。

Exact 仍可能扫描全量

Local Top-k 先减少物化和通信，不会自动把 O(L) 变成 O(k)。

更细访存不是魔法

效果仍取决于 KV layout、block alignment、bank mapping 和访问合并。

参考零件不等于完整方案

TMA、SparseCore 或 DIMC 能提供启发，不等于已经实现完整 Indexer。

不要把模型公式焊死

固化 DOT、REDUCE、TOPK、GATHER 等原语，把模型变化留给编译器。

术语索引｜把术语翻译成“它在系统里做什么”
Tensor Plane
负责规则矩阵与向量计算的主计算平面。
Retrieval Plane
本文提出的 Search、Select、Move、Route、Address 数据流平面。
Local Top-k
每个分区先保留自己的前 k 个候选，再做全局合并。
Gather descriptor
描述要读取哪些 KV 页和地址，供搬运引擎直接消费。
TPOT / TTFT
每个输出 token 的时间 / 生成首 token 的时间。
HBM bytes/token
生成一个 token 需要从高带宽内存读写的数据量。
Exact
保持候选选择语义；是否全量扫描取决于算法与索引。
Approximate
通过额外结构少看候选，需要单独验证 recall 和模型质量。

06 / 评价方法

创新不等于“参数更大”，而是有没有换一条有效路径。

沿用引用会话的权重。分数用于帮助读者比较架构思想的不同，不代表真实部署性能、成本或商业成功。

30%

数据搬运与存储
片上 SRAM、HBM、内存层级、数据是否必须来回写回。

20%

执行架构
矩阵、向量、标量、稀疏、数据流等执行单元怎么分工。

是否考虑 Top-k、Gather、MoE routing、embedding 或动态 shape。

数值与密度

10%

可编程性
编译器、ISA、运行时能否吸收模型变化，而不是焊死一个公式。

读分数的方式：高分说明“架构问题意识”和“可供下一代 Retrieval GPU 研究的价值”高；它不自动说明芯片对所有模型更快。尤其要把官方峰值、平台级带宽与真实 TPOT、Tokens/J、Top-k recall 分开。

07 / 交叉洞察

下一颗推理芯片，可能不是“更大的矩阵工厂”。

十条路线交叉后，最值得追踪的不是一个冠军，而是三种能力正在靠近同一个系统问题。

Tensor + Sparse + Dataflow

密集矩阵单元继续负责规则吞吐；Sparse/Vector 单元负责不规则动作；编译器或硬件事件图负责把“算—筛—搬—算”串成连续流水。

附件提出的 Retrieval Plane，真正可以从这些成熟零件中吸收的是数据路径与执行边界，而不是照搬某颗芯片的宣传数字。

先验证数据流，再决定划硅

  • Exact Local Top-k → Global Merge
  • 减少 score materialization 与跨卡全量 reduction
  • 输出 page-aware Gather descriptor
  • 用 TPOT、HBM bytes/token、inter-GPU bytes/token、Tokens/J 做 Go / No-Go
